技术面试参考答案

一、数据系统基础与架构设计

1. 数据系统的定义与交互

数据系统是对业务系统产生的数据进行采集、存储、加工、分析和服务的一整套技术体系。

闭环协同流程（记忆口诀：采-存-算-用-反）：

  • 采：从业务系统采集数据（Binlog、埋点、日志、API）
  • 存：统一存入数据湖/数仓（ODS层落地）
  • 算：分层加工（DWD→DWS→ADS），产出指标和标签
  • 用：通过报表、数据服务API、特征服务等对外提供
  • 反：反哺业务——如用户画像驱动精准营销、风控模型实时拦截、推荐算法提升转化

面试加分点： 强调”数据系统不是被动的存储，而是主动的价值创造者”。

2. SLA设计与沟通决策

SLA设计三要素：

  • 时效性：数据从产生到可查询的延迟（T+1 / 小时级 / 分钟级 / 秒级）
  • 准确性：数据质量达标率（如 ≥99.9%）
  • 可用性：服务可用时间占比（如 99.95%）

面对”分钟级可见”高成本需求的决策逻辑：

  1. 先问Why：这个需求背后的业务场景是什么？是实时大屏监控还是运营看板？
  2. 量化成本：分钟级 vs 小时级，基础设施成本可能差5-10倍
  3. 分级处理：核心指标做分钟级，非核心指标做小时级或T+1
  4. 给替代方案：比如”核心3个指标做实时，其余50个指标做T+1，成本降低80%”

沟通话术： “我完全理解实时性的价值。我建议我们把指标分成三档——秒级、分钟级、小时级，核心决策指标优先保障实时，这样既满足业务需求，成本也可控。”

3. 数仓分层规范与调整

经典分层职责：

层 职责 关键词
ODS 原始数据落地，不做加工 原样保留
DWD 明细数据，清洗+标准化+维度退化 一行一事实
DWS 轻度汇总，公共指标 按主题聚合
ADS 应用层，面向具体场景 直接消费

DWD层轻度聚合是否合理？ 一般不推荐，但以下场景可以打破：

  1. 日志去重场景：用户行为日志一天几十亿条，在DWD层按session聚合是合理的
  2. 多源合并场景：同一业务事件分散在多个系统，DWD层做合并拼接
  3. 性能瓶颈场景：下游所有任务都需要同样的聚合，提前在DWD做可以避免重复计算

原则： 打破规范要有充分理由，且需要在文档中明确标注，避免后续维护混乱。

4. ODS直接查询需求应对

三个角度说服：

角度 问题 话术
技术可行性 ODS数据未清洗，字段含义不明确，关联查询复杂 “ODS是原始数据，字段可能有脏数据和歧义，直接查容易得出错误结论”
数据管理 绕过分层体系，口径不统一，指标打架 “如果每个人都查ODS自己算，同一个指标可能出现多个不同的数字”
成本控制 ODS数据量大，全表扫描成本高 “ODS层数据量是DWS的100倍，一次查询可能扫描几TB”

替代方案：

  • 紧急需求：提供DWD层的自助查询权限
  • 探索性需求：搭建数据沙箱，用ODS的采样子集
  • 长期需求：纳入需求排期，在ADS层建设标准数据产品

5. 数据服务化

核心理解（记忆口诀：统一入口、按需交付、质量可控）：

  • 定义：将数据能力封装为标准化的API服务，让业务方像调用微服务一样获取数据
  • 核心能力：统一查询网关、多数据源路由、缓存加速、限流熔断、权限管控
  • 实现方式：数据服务中台，底层对接多种引擎（MySQL/ClickHouse/Redis/ES），上层提供统一RESTful API
  • 价值：
    • 解耦：业务不需要知道数据存在哪里
    • 复用：同一个接口多个业务方共享
    • 管控：统一的权限、审计、监控

6. 开发规范与最佳实践

六大关键规范（记忆口诀：命-版-测-审-发-监）：

  1. 命名规范：表名 层级_业务域_主题_描述，如 dwd_trade_order_detail
  2. 版本管理：SQL脚本全部入Git，PR review后才能合并
  3. 测试流程：开发环境→测试环境（用脱敏数据验证）→生产环境
  4. 代码审查：SQL必须经过同行review，重点看性能和口径
  5. 发布策略：灰度发布，先跑新旧两套对比，数据一致后再切换
  6. 监控告警：每个任务配置数据量波动、空值率、时效性告警

二、计算引擎与数据处理

7. Spark与Flink对比

核心区别：

维度 Spark Streaming Flink
计算模型 微批（Micro-Batch） 真正的逐条流处理
延迟 秒级（取决于批次间隔） 毫秒级
状态管理 有限支持 原生强大的状态管理
窗口 基于时间的简单窗口 丰富的窗口语义（滚动/滑动/会话）
适用场景 批处理为主+准实时 实时计算为主

Checkpoint vs Savepoint：

  • Checkpoint：自动触发，用于故障恢复，轻量级，由Flink管理生命周期
  • Savepoint：手动触发，用于版本升级/任务迁移，完整快照，用户管理生命周期

记忆口诀： Checkpoint是”自动存档”，Savepoint是”手动存档”。

State Backend选择：

  • HashMapStateBackend：状态存内存，速度快，适合状态小的场景（<几GB）
  • EmbeddedRocksDBStateBackend：状态存磁盘，适合超大状态（TB级），吞吐略低

8. 拉链表设计

原理一句话： 用起止时间记录每条数据的每个历史版本，实现”任意时间点回溯”。

表结构关键字段：

适用场景： 缓慢变化的维度数据（用户信息、商品属性），变化频率不高但需要保留历史。

设计要点：

  • end_date = 9999-12-31 表示当前有效记录
  • 每日增量更新：新数据来了→关闭旧记录（更新end_date）→插入新记录
  • 查询某天快照：WHERE start_date <= '目标日期' AND end_date >= '目标日期'
  • 注意分区策略：按 end_date 分区，当前有效数据集中在一个分区，查询高效

9. MPP架构解析

一句话定义： 多个独立节点各自拥有CPU/内存/存储，并行处理数据，最后汇总结果。

核心特点（记忆：独立、并行、无共享）：

  • Shared-Nothing：每个节点独立，不共享资源
  • 数据分片：数据按规则分布到各节点
  • 并行计算：每个节点只处理自己的数据分片
  • 协调汇总：最终由协调节点合并结果

代表产品：

  • Greenplum：基于PostgreSQL的MPP数据库，适合复杂SQL分析
  • ClickHouse：列式存储+MPP，极致的OLAP查询性能

优势： 线性扩展能力强，PB级数据秒级响应。
局限： 节点间数据shuffle开销大，不适合高并发点查。

10. 数据倾斜问题

产生原因： 数据分布不均匀，导致某些Task处理的数据量远大于其他Task。

常见场景： Join时某个key特别多（如 null、-1、热门商品ID）、Group By时某个分组特别大。

处理方法大全：

方法 原理 适用场景
加盐（Salting） 给倾斜key加随机前缀打散 通用
Map端聚合 先在Map端预聚合减少数据量 Group By倾斜
广播小表 小表广播避免Shuffle 大小表Join
过滤空值 单独处理null key null导致的倾斜
调整并行度 增加partition数 轻度倾斜
两阶段聚合 先局部聚合再全局聚合 聚合类倾斜

Spark Skew Join优化参数：

  • spark.sql.adaptive.skewJoin.enabled = true（开启AQE自适应倾斜处理）
  • 原理：运行时检测到某个partition过大，自动将其拆分成多个小partition分别与对应数据join

业务逻辑预处理策略：

  • 提前过滤无效数据（如测试账号、爬虫流量）
  • 热点数据单独处理（如头部商家单独一条链路）
  • 维度预聚合（在DWD层就按业务含义做预聚合）

11. 数据倾斜自愈框架

设计思路（记忆：监-判-治-验）：

  1. 监控指标：

    • 各Task的数据量/处理时间的方差和极差
    • Shuffle Read/Write的数据量分布
    • GC时间、OOM频率

  2. 触发阈值：

    • 最大Task数据量 > 中位数的 N倍（如5倍）
    • 单Task处理时间 > 平均值的 10倍
    • 连续M次运行出现同样的倾斜pattern

  3. 执行策略（渐进式）：

    • Level 1：自动增加并行度（调大shuffle partition数）
    • Level 2：开启AQE自适应优化
    • Level 3：自动对倾斜key加盐重写SQL
    • Level 4：告警通知人工介入

  4. 验证闭环： 修复后对比前后的执行时间和资源消耗，确认优化有效

三、实时计算与架构

12. 实时数仓架构设计

整体架构（Kappa + Lambda混合）：

四个核心问题的回答：

流批一体实现：

  • 存储层统一：用Iceberg/Hudi同时支持流读和批读
  • 计算层统一：Flink SQL同一套代码，流批两种执行模式
  • 口径统一：流和批共用同一套指标定义

状态管理：

  • 使用Flink的RocksDB State Backend处理大状态
  • 合理设置State TTL，避免状态无限膨胀
  • 定期做Savepoint用于版本升级

乱序数据处理：

  • 设置合理的Watermark策略（如允许5秒乱序）
  • 使用Event Time而非Processing Time
  • 迟到数据通过Side Output收集，走修正链路

实时数仓分层：

层 存储 职责
ODS Kafka 原始数据接入
DWD Kafka 实时清洗、维度关联
DWS ClickHouse/Doris 实时聚合指标
ADS Redis/MySQL 面向应用的实时服务

四、云原生与成本治理

13. 云上架构与成本优化

架构选型决策：

  • Serverless（如AWS Lambda/EMR Serverless）：适合波峰波谷明显、突发性计算任务
  • 容器化（K8s + Spark on K8s）：适合常驻服务、需要精细资源控制的场景

弹性伸缩策略：

  • 计算层：基于任务队列深度自动扩缩容
  • 存储层：冷热分层（热数据SSD，温数据HDD，冷数据对象存储）

成本优化六招：

  1. 存储分层：按访问频率自动降级存储类型
  2. 竞价实例：非关键批处理任务使用Spot实例，成本降60-80%
  3. 资源池化：多团队共享资源池，提高利用率
  4. 任务调度优化：错峰调度，避免资源争抢
  5. 数据生命周期：自动清理过期数据
  6. SQL治理：识别低效SQL，优化或下线

14. 运维与可观测性体系

监控告警关键指标（记忆：时-量-质-资）：

  • 时效：任务是否按时完成，延迟多少
  • 数据量：与历史同期对比，波动是否异常
  • 质量：空值率、重复率、枚举值分布
  • 资源：CPU/内存/磁盘使用率，队列排队时间

故障自愈机制：

  • 任务失败自动重试（可配置重试次数和间隔）
  • 资源不足自动扩容
  • 上游延迟自动调整下游调度时间
  • 数据质量不达标自动阻断下游任务

可观测性三支柱： Metrics（指标）+ Logging（日志）+ Tracing（链路追踪）

  • 数据血缘可视化：任意指标可追溯到源头
  • 任务依赖DAG可视化：一眼看出影响范围

五、软技能与架构决策

15. 技术选型与团队协作

技术选型方法论（记忆：需-评-验-决）：

  1. 需求分析：明确业务场景、数据量级、性能要求、团队技术栈
  2. 方案评估：列出候选方案，从功能、性能、成本、生态、运维难度五个维度打分
  3. POC验证：用真实数据做小规模验证，而非只看官方benchmark
  4. 决策记录：用ADR（Architecture Decision Record）记录决策过程和理由

技术债务管理：

  • 建立技术债务清单，按影响程度和修复成本排优先级
  • 每个迭代预留20%时间偿还技术债
  • 新需求开发时”顺手”修复相关技术债

跨团队协作案例模板：

“在XX项目中，我作为数据架构师，协调了业务团队、数据团队和基础架构团队。核心问题是XX。我的做法是：先拉齐各方对问题的理解，然后制定分阶段方案，每周同步进展。最终在X个月内完成了XX，效果是XX。”

六、数据治理与建模

16. 数据治理体系

四大核心范畴（记忆：质-元-血-安）：

范畴 核心内容
数据质量 完整性、准确性、一致性、及时性；建立质量规则引擎，自动检测+告警+阻断
元数据管理 技术元数据（表结构、字段类型）+ 业务元数据（指标定义、口径说明）+ 操作元数据（ETL日志、调度信息）
血缘追踪 表级→字段级血缘，支持影响分析（改一个字段影响哪些下游）和溯源分析（一个指标从哪来）
安全合规 数据分级分类、脱敏规则、访问权限控制、审计日志；GDPR要求数据可删除/可导出，等保2.0要求访问控制+审计

17. 维度建模 vs OLTP建模

本质区别：

维度 OLTP建模 维度建模
目标 减少冗余，保证事务一致性 优化查询性能，方便分析
范式 三范式（3NF） 星型/雪花模型
冗余 尽量消除 适度冗余换性能
设计驱动 实体关系驱动 业务分析需求驱动

DWD层为什么用宽表？

  • 避免运行时多表Join，查询性能提升数倍
  • 分析师可以直接使用，降低使用门槛
  • 列式存储下，不查的列不读，宽表的存储开销可控

宽表膨胀控制：

  • 只退化高频使用的维度属性，不是所有维度都塞进来
  • 按业务主题拆分宽表，而非一张”超级大宽表”
  • 低频维度通过维度表关联获取
  • 定期review字段使用率，下线无人使用的字段

18. 应对频繁变更的维度建模

SCD策略选择：

类型 策略 适用场景
SCD1 直接覆盖，不保留历史 修正错误数据
SCD2 拉链表，保留完整历史 需要历史回溯（最常用）
SCD3 增加”上一次”字段 只需保留最近一次变更
SCD混合 核心属性用SCD2，非核心用SCD1 平衡存储和需求

频繁变更的设计建议：

  • 将稳定属性和易变属性分开建表（Mini-Dimension技术）
  • 易变属性用SCD2拉链表，稳定属性用SCD1
  • 设置合理的变更检测粒度（如每天只取最后一次状态，避免一天内多次变更产生过多版本）

19. 数据湖格式对比

能力 Delta Lake Iceberg Hudi
ACID事务 支持 支持 支持
时间旅行 支持 支持（快照机制更优） 支持
Schema演化 支持 最灵活（列级演化） 支持
生态绑定 强绑Spark/Databricks 引擎无关（最开放） 偏Spark/Flink

  • Delta Lake：OPTIMIZE命令 + Z-ORDER排序
  • Iceberg：后台自动Compaction，Rewrite Data Files
  • Hudi：Compaction机制（MOR表自动合并log文件和base文件）

20. 湖仓一体架构设计

核心设计思路：

三个核心问题：

统一元数据管理：

  • 用统一的Catalog管理所有表的元数据
  • 数据湖表和数仓表共享同一套元数据定义
  • 支持跨引擎的元数据访问

ACID保证：

  • 依赖数据湖格式（Iceberg/Hudi）提供的事务能力
  • 写入时通过乐观并发控制保证一致性
  • 支持快照隔离，读写互不阻塞

流批一致性：

  • 流式写入和批量写入写同一张表
  • 通过Watermark和Checkpoint保证Exactly-Once语义
  • 批处理定期做数据修正，流处理保证时效性

面试通用技巧

  1. 回答结构：先给结论，再展开细节（金字塔原理）
  2. 举例说明：每个理论点尽量配一个实际场景
  3. 展示思考：不只说”怎么做”，更要说”为什么这么做”
  4. 承认边界：不确定的地方坦诚说”这块我了解有限，但我的思路是…”

Canal介绍与使用

简介

**canal [kə’næl]**，译意为水道/管道/沟渠，主要用途是基于 MySQL 数据库增量日志解析，提供增量数据订阅和消费

早期阿里巴巴因为杭州和美国双机房部署，存在跨机房同步的业务需求，实现方式主要是基于业务 trigger 获取增量变更。从 2010 年开始，业务逐步尝试数据库日志解析获取增量变更进行同步，由此衍生出了大量的数据库增量订阅和消费业务。

基于日志增量订阅和消费的业务包括

  • 数据库镜像
  • 数据库实时备份
  • 索引构建和实时维护(拆分异构索引、倒排索引等)
  • 业务 cache 刷新
  • 带业务逻辑的增量数据处理

当前的 canal 支持源端 MySQL 版本包括 5.1.x , 5.5.x , 5.6.x , 5.7.x , 8.0.x

注意：本文中使用的canal版本为1.1.7版本

更多详细内容可以参考Home · alibaba/canal Wiki (github.com)

工作原理

MySQL主备复制原理

  • MySQL master 将数据变更写入二进制日志( binary log, 其中记录叫做二进制日志事件binary log events，可以通过 show binlog events 进行查看)
  • MySQL slave 将 master 的 binary log events 拷贝到它的中继日志(relay log)
  • MySQL slave 重放 relay log 中事件，将数据变更反映它自己的数据

canal 工作原理

  • canal 模拟 MySQL slave 的交互协议，伪装自己为 MySQL slave ，向 MySQL master 发送dump 协议
  • MySQL master 收到 dump 请求，开始推送 binary log 给 slave (即 canal )
  • canal 解析 binary log 对象(原始为 byte 流)

架构与概念

  • canal是一个CS架构的程序，因此分为client与server,其中server可以包含多个instance
  • server：代表一个canal运行实例，对应于一个jvm，本质是一个基于SpringBoot的Web项目（包含Netty和Embeded两种实现），可以通过接口启动、配置、调度、监控instance
  • instance：对应于一个数据队列，这个数据队列会完成解析binlog日志、binlog日志过滤、 binlog日志转储、位点元数据管理等核心功能,instance包含以下四个核心组件：
    • eventParser :数据源接入，模拟slave协议和master进行交互，协议解析
    • eventSink :Parser和Store链接器，进行数据过滤，加工，分发的工作
    • eventStore :数据存储，目前仅实现了Memory内存模式
    • metaManager :增量订阅&消费信息管理器
  • client：消费数据的客户端，可以自己参考官方demo写java实现，也可以直接使用官方提供的工具包（CilentAdapter）

相关组件

  • canal.deployer:canal主体程序

  • canal.admin:canal 的Web版管理后台，可以通过图形化界面管理配置参数,从而动态启停 Server 和 Instance，本文对此不多做深入研究

  • canal.adapter:应当称为ClientAdapter,是在canal 1.1.1版本之后, 增加的客户端数据落地的适配及启动功能，目前支持功能:

    • 客户端启动器
    • 同步管理REST接口
    • 日志适配器, 作为DEMO
    • 关系型数据库的数据同步(表对表同步), ETL功能
    • HBase的数据同步(表对表同步), ETL功能
    • ElasticSearch多表数据同步,ETL功能

另外还有集群HA的解决方案，但是目前暂时够用未深入研究

一般来说，用一个server带起若干instance，再加上adapter已经足够普通用户的使用

上图可以看出，Swarm是典型的master-slave结构，通过发现服务来选举manager。manager是中心管理节点，各个node上运行agent接受manager的统一管理，集群会自动通过Raft协议分布式选举出manager节点，无需额外的发现服务支持，避免了单点的瓶颈问题，同时也内置了DNS的负载均衡和对外部负载均衡机制的集成支持。

  • node（节点）: 一个节点是docker引擎集群的一个实例，也可以将其视为一个Docker节点。可以在单个物理计算机或云服务器上运行一个或多个节点，但在部署生产集群时通常将节点分布部署在多个物理和云计算机上。
    要将应用程序部署到swarm，需要将服务定义信息提交给 manager node(管理节点)。管理节点将称为tasks(任务)的工作单元分派给 worker nodes(工作节点)。
    管理节点还执行编排和集群管理功能，从而使群集处于需要的状态。管理节点会    选举    一个领导者来执行编排任务。
    工作节点接收并执行从管理器节点分派的任务。默认情况下，管理器节点也可以作为工作节点运行，但可以将它们配置为仅运行管理任务并且仅是管理节点。代理程序在每个工作节点上运行着一个代理程序，这个代理程序会报告分配给这个工作节点的任务的详细信息。工作节点会通知管理节点分配给它的任务的当前状态，以便管理节点可以维护每个工作节点的状态。

  • service(服务)：服务是要执行在节点上的一组task（任务）的定义，它是集群系统的核心结构，同时也是用户与swarm系统进行交互的核心内容。Service有两种运行模式，一种是replicated，swarm会将服务所需的任务按照你定义的数量复制部署在多个节点上；另一种是global，在所有符合运行条件的Node上，都运行一个服务所需的任务。

  • task(任务):一个任务是一个docker容器和容器内运行命令的集合。它是swarm任务调度的原子单位，管理节点会根据服务内对任务的定义将任务分派到工作节点，一旦一个任务分配到了一个节点，这个任务就不能再移动都其它节点，他只能再一开始分派到的节点上运行或者直到失败。

  • 负载均衡：swarm使用了入口负载均衡器来把服务开放给swarm外部，swarm可以自动给服务分配外部端口也可以由用户自定义外部端口，如果用户不定义外部端口的话，swarm会在30000~3276这个范围内随机给服务分配一个端口。外部组件比如云负载均衡器或者nginx之类的组件，可以从集群内的任意一个节点（无论该节点是否在运行要访问服务的任务）来访问服务。所有集群内节点都可以路由入口连接到一个运行着任务的实例。另外swarm模式还有一个内部DNS组件来给服务自动分派一个DNS入口。swarm manager使用一个内部负载均衡器根据每个服务的DNS地址来分配集群内服务的请求。

Why

为什么使用docker swarm，其实也就是一些功能特点，满足了需求就用：

  1. 与Docker Engine集成的集群管理:使用Docker Engine CLI创建一组Docker引擎，您可以在其中部署应用程序服务。您不需要其他编排软件来创建或管理群集。

  2. 节点分散式设计：Docker Engine不是在部署时处理节点角色之间的差异，而是在运行时处理角色变化。您可以使用Docker Engine部署两种类型的节点，管理节点和工作节点。这意味着您可以很方便地从单个镜像开始构建整个群集。

  3. 声明式服务模型：Docker Engine使用声明式方法来定义应用程序堆栈中各种服务的所需状态。例如，您可以描述由具有消息队列服务和数据库后端的Web前端服务组成的应用程序。

  4. 可扩容与缩放容器：对于每个服务，您可以声明要运行的任务数。当您扩容或缩放时，swarm管理器通过添加或删除任务来自动适应，以保持所需的任务数量来保证集群的可靠状态。

  5. 容器容错状态协调：集群管理节点不断监视群集状态，并协调期望状态与实际状态之间的任何差异。例如，如果设置了一个运行10个副本容器的服务，然后托管其中两个副本容器的工作节点崩溃了，那么管理器将创建两个新副本容器以替换崩溃的副本容器。 swarm管理器将新副本容器分配给正在运行和可用的工作节点上。

  6. 多主机网络：您可以为服务指定承载网络。当swarm管理器初始化或更新应用程序时，它会自动为承载网络上的容器分配地址。

  7. 服务发现：Swarm管理节点为swarm中的每个服务分配唯一的DNS名称，并对运行的容器进行负载均衡。您可以通过嵌入在swarm中的DNS服务器查询在集群中运行的每个容器。

  8. 负载均衡：您可以将服务的端口公开给外部负载平衡器。在内部，swarm允许您指定如何在节点之间分发服务容器。

  9. 缺省安全：集群中的每个节点强制执行TLS验证和加密，以保护其自身与所有其他节点之间的通信。可以选择使用自签名根证书或来自自定义根CA的证书。

  10. 滚动更新：在已经运行期间，您可以增量地应用服务更新到节点。 swarm管理器允许您控制将服务部署到不同节点集之间的延迟。如果出现任何问题，您可以将任务回滚到服务的先前版本。

需要区分两种环境变量，一种指传递到容器内部的环境变量，一种指docker-compose.yml文件中通过${}符号引用用于设置docker-compose的环境变量。

前者的优先级从低到高如下：

  1. docker-compose.yml中声明env_file
  2. docker-compose.yml声明environment

后者的优先级从低到高如下：

  1. 同一目录下放一个.env文件

  2. 在/etc/profile或者在shell中通过export设置环境变量

Theory Summary

Markowitz made the following assumptions while developing the Mean-Variance Model:

  1. Risk of a portfolio is based on the variability of returns from the said portfolio.
  2. An investor is risk averse.
  3. An investor prefers to increase consumption.
  4. The investor’s utility function is concave and increasing, due to his risk aversion and consumption preference.
  5. Analysis is based on single period model of investment.
  6. An investor either maximizes his portfolio return for a given level of risk or maximizes his return for the minimum risk.
  7. An investor is rational in nature.

To choose the best portfolio from a number of possible portfolios, each with different return and risk, two separate decisions are to be made, detailed in the below sections:

  1. Determination of a set of efficient portfolios.
  2. Selection of the best portfolio out of the efficient set.

These return series can be used to create a wide range of portfolios. After that random weight vectors and plot those portfolios will be produced. As I want all my capital to be invested, the weights will have to sum to one.

Next, evaluate how these random portfolios would perform by calculating the mean returns and the volatility (here using standard deviation). I set a filter so that only portfolios with a standard deviation of < 2 are ploted for better illustration.

Calculate the return using

R=pTw

where R is the expected return, pT is the transpose of the vector for the mean returns for each time series and w is the weight vector of the portfolio. p is a N*1 column vector, so pT turns is a 1*N row vector which can be multiplied with the weight (column) vector w to give a scalar result.

Next, Calculate the standard deviation

sigma=sqrt(wTCw)

where C is the N*N covariance matrix of the returns.

Now the efficient frontier in Markowitz-style can be calculated. This is done by minimizing
